# 08：评估、交付与接下来学什么

## 跑通一次不是做完了

模型输出会变化。提示词改得更长、回复更流畅，都不直接证明任务做得更好。先定义可验证的成功标准，再比较改动。

对当前乘法 Agent，“正确”至少包含：使用获准工具；参数符合题意；程序执行结果正确；结果回填关联正确；最终答案正确；调用次数在预算内。只检查回复里有“391”会漏掉伪造工具结果的问题。

## 做一张小而固定的评估表

现有 `demos/advanced/advanced_03_evaluation.py` 默认离线运行固定计算用例；`--live` 改用真实 DeepSeek。具体实验见 [高级 A03](../levels/advanced.md)。

| 用例 | 期望行为 | 验证方法 |
|---|---|---|
| 17×23 | 工具结果 391，答案一致 | 校验工具输出和答案 |
| 0×25 | 得到 0，不把 0 误当空结果 | 确定性断言 |
| 两个独立乘法 | 每个请求都有配对结果 | 检查 tool call ID |
| 未注册工具 | 不执行，返回错误 | 白名单测试 |
| 参数不是 JSON | 返回错误而非崩溃执行 | 假响应测试 |
| 工具无限循环 | 达到预算后停止 | 轮次和调用计数 |
| 模型 HTTP 失败 | 不产生伪造回答，保留错误 trace | 假 HTTP + 观测断言 |
| 流式中断 | 不把半句当完整回复 | 检查中断状态 |
| 敏感字段 | 上报副本不含测试秘密 | 检查 exporter 中的内容 |
| 上报失败 | 模型逻辑不被导出故障覆盖 | 故障 exporter 测试 |

测试代码已实现这类契约检查。它们验证程序行为；真实模型是否选择正确工具，需要另一组端到端实验。

## 两种验收分开运行

离线回归：

```bash
uv run python -m unittest discover -s tests -v
```

真实接口与入库：

```bash
uv run python verify_live.py
```

后者默认覆盖全部三级，包括思考模式、检索、会话保存和资料 Agent，通常共 13 次模型请求；可用 `--level beginner|intermediate|advanced` 单独验收。脚本同时检查具体业务答案、工具实际结果、全部 span 数量、父子关系、正文、用量和密钥未进入记录。添加 `--evaluate` 再执行四个计算用例并查回 trace。它不等于所有任务的质量基准或生产验收。

比较提示词或模型时，保持问题集不变，记录配置版本、成功率、平均调用次数、token 与耗时。抽样人工评估开放式回答；精确计算和结构约束优先用确定性检查。若以后使用模型做评分，该评分调用也需要记录和预算，并且评分本身可能有偏差。

## 毕业项目：只读资料助手

当前 `demos/advanced/advanced_04_knowledge_agent.py` 已实现基于三份虚构资料的只读命令行助手，可先运行再扩展到十篇自建说明文档。要求：有固定资料目录；能检索并给出处；资料无答案时明确说明；所有模型请求和工具步骤可观察；限制轮次和输入长度；不得修改资料或任意执行命令。

建议按顺序交付：先固定检索流程并验证答案；再将检索注册成工具；再增加持久化会话；最后加入结构化结果和一组评估用例。每次扩展都比较同一批问题。不要同时加入搜索、浏览器、数据库写入和多 Agent 协作，出了错会难以定位。

验收时选一道正确题、一道无答案题、一道包含干扰指令的资料题。展示用户输入、检索依据、工具实际返回、最终答案和 trace。这比展示一段“看起来很聪明”的聊天更能说明系统可靠。

## 从命令行到服务

完成底层实验后，再考虑 HTTP 服务、请求验证、用户身份、会话隔离、并发限制、取消、总超时、限流、密钥管理、故障告警、部署与回滚。同步教学客户端适合本机实验，不能直接当作高并发生产服务。

需要并发时可以学习 `asyncio` 和异步 HTTP；工具有依赖时不能随意并发。需要长任务时再学习任务队列与恢复。多个 Agent 的本质仍是多组消息、多个循环、状态交接和更多模型请求，先能评估单个 Agent，再决定分工是否有收益。

## 什么时候再学框架

当你能解释以下问题，就适合阅读框架的实现并比较它替你封装了什么：

1. 谁构造 messages，谁保存历史？
2. 谁读取 tool_calls，谁真正执行函数？
3. 工具结果如何配对并进入下一轮？
4. 什么时候停止，错误如何传播，预算如何累计？
5. 一次用户运行怎样关联到所有模型请求与工具动作？
6. 进程中断后哪些状态可能丢失，哪些动作不能重复执行？

届时再评价框架是否解决了你遇到的具体问题，而不是把 API 名字当成 Agent 原理。当前所有实验继续保持普通 Python 与显式 HTTP。
