# 02：消息、上下文与 token

## 模型怎样“记住”上一句话

在本课程使用的 Chat Completions 调用方式中，程序显式传入对话历史。第一次说“小猫叫豆包”，第二次只发送“它叫什么”，模型没有收到第一句话就缺少依据。多轮示例把历史保存在 Python 列表里。

```python
messages.append({'role': 'user', 'content': question})
data = model.chat(messages)
messages.append(message_of(data))
```

顺序很重要：先加入当前问题，再调用模型，再保存模型回复。下一轮发送增长后的列表。运行 `uv run python -m demos.beginner.beginner_02_messages`，在同一个 trace 中比较两个模型 span 的 `app.request`。

## 四类角色

| role | 谁提供 | 在本项目中的含义 |
|---|---|---|
| `system` | 应用开发者 | 行为约束、任务范围、输出要求 |
| `user` | 使用者或应用传入材料 | 当前问题和资料 |
| `assistant` | 模型 | 已生成的文本或工具请求 |
| `tool` | 你的程序 | 实际执行结果，带 `tool_call_id` |

角色告诉模型如何理解材料，但角色本身不能代替权限控制。用户上传的网页即使写着“忽略之前规则”，仍是待处理资料，不应被你的程序提升为 system 指令。真正能否读文件、访问数据库或发消息，由程序检查权限。

## 上下文、记忆、缓存不是同一个东西

**上下文**是这次请求里的材料，包含指令、历史、检索内容和工具结果。**会话历史**是你的应用保存的消息。**长期记忆**是经筛选后持久化的数据，下次需要时再取出。**服务端缓存**用于优化重复前缀的计算；它不等于让应用可以省略历史。

关掉程序后，示例里的列表就消失了；当前没有数据库或跨进程记忆。不要把这一点误以为是模型接口故障。

## token 是什么，为什么第二轮常更贵

Token 是模型处理文本时使用的编码单位，不严格等于一个字或一个单词。中文、英文、标点和代码的切分都可能不同。精确用量以返回的 `usage` 为准。

第二轮再次发送第一轮历史，所以输入 token 通常增加。假设三轮的输入分别是 100、150、210 token，输出分别是 50、60、40，那么三次累计处理 610 token。这里是示意算术，不代表定价。费用还取决于模型、输入/输出类别与缓存命中情况。

当前 span 单独记录每轮的输入、输出 token，也保留缓存命中字段；根 span 的 `app.total_tokens` 累加服务端已知用量。网络断开时拿不到 usage，不能把“未知”认定为“没有消耗”。

## 上下文为什么要管理

历史一直追加会带来三件事：请求变大、成本增加、无关信息干扰任务。最简单的策略是只保留最近几轮；随后可以增加摘要、检索和外部状态。

工具对话不能随意切半：保留一条 assistant 工具调用时，要同时保留对应的 tool 结果，避免孤立的调用或结果。摘要也可能遗漏信息，应保留关键事实来源，并允许重读原文。

本节先不实现自动压缩，先观察历史到底多了什么。不要过早让一个“记忆组件”把这些细节遮住。

## 实验与自检

1. 运行多轮脚本，找出第二次 `app.request.messages` 中新增的消息。
2. 临时让第二轮只发送最后一条 user 消息，观察失去历史后的回答，然后恢复。
3. 增加第三轮“把这个名字写进一句话”。比较三轮 `prompt_tokens`，解释增长原因。

答案要点：模型在一次请求中只获得你发送的材料；对话连贯来自客户端维护状态。上下文管理既影响成本，也影响回答质量。需要长期保存的内容应由应用明确决定，不把全部聊天无限保存当作设计方案。
