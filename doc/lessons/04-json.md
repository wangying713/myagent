# 04：让输出能被程序可靠使用

## 一段自然语言还不够

“帮我买三本笔记本”如果要进入订单流程，程序希望得到固定字段，而不是从一大段回答中猜出数量。这里先做**信息提取**，不真正下单。

```bash
uv run python -m demos.intermediate.intermediate_01_json
```

脚本要求模型输出 JSON，并设置 `response_format={'type': 'json_object'}`。提示中明确提到 JSON 和示例结构，参见 [DeepSeek JSON Output](https://api-docs.deepseek.com/guides/json_mode/)。返回的 `message.content` 仍是字符串，需要 `json.loads()`。

## 三层验证

| 层次 | 示例问题 | 当前怎么处理 |
|---|---|---|
| 语法 | 是不是完整 JSON？ | 客户端检查结束原因，随后 `json.loads()` |
| 结构 | quantity 是整数吗？多了字段吗？ | `parse_order()` 检查键、类型和范围 |
| 业务事实 | 用户真的说了三本吗？商品是否存在？ | 还需要对照原始输入与业务数据；schema 不会替你证明 |

`{"item":"笔记本","quantity":3}` 是示例，不是必须逐字复现的答案。数量范围被业务规则限制为 1–100，即使模型给出语法正确的 1000，也应被应用拒绝。

本例只使用普通 Python 校验；以后可以学习 JSON Schema 校验库或数据模型库。理解校验层次比先记住库的用法更重要。

## JSON 输出和工具调用怎么选择

目标是提取一个给程序使用的结果时，可以使用结构化输出。目标是让模型请求应用执行某个能力时，使用工具调用。两者都可能涉及 JSON，但前者是结果格式，后者还有调用 ID、执行与结果回填的协议。

工具参数即便通过 schema 约束，也应检查权限和业务条件。例如一个“转账金额”字段类型正确，并不意味着用户已授权转账。本课程工具只有无副作用的乘法。

## 错误怎样处理

如果响应截断，不能随手补一个右括号就当正确数据。如果字段缺失，应明确报错或向用户补充询问；不要私自发明关键值。允许模型修复时应限制修复次数，并把第二次请求作为新的模型调用记录，不能无限重试。

当前客户端在模型层发现 `length` 时直接报错；应用层 `parse_order()` 失败时，运行根 span 标记 ERROR，而模型 span 仍可正常。这说明“模型协议完成”和“业务验收通过”是两件事。

## 实验与自检

1. 把数量改成五本，核对终端数据及 trace 响应。
2. 将输入改成一百零一本，观察程序拒绝越界数量。
3. 离线调用 `parse_order('{"item":"笔","quantity":true}')`，理解为什么 bool 不应当作数量。
4. 思考“帮我买一些笔记本”应怎么处理。当前教学函数无法可靠表达“数量未知”；正式设计可以增加明确的缺失状态，再问用户。

学会的标志：能清楚说出“JSON 可解析”为什么不等于“可以直接执行业务操作”。
