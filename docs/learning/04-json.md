# 04：结构化输出与业务校验

**状态：后续课程，Go 版本尚未实现。** 当前三课没有结构化订单接口或 `response_format` 参数。本节迁移原理和练习目标，不提供不存在的运行命令。

## 一段自然语言为何不够

“帮我买三本笔记本”适合练习信息提取：希望得到 `{"item":"笔记本","quantity":3}`，先不真正下单。即使未来模型端点支持 JSON 输出约束，回答正文仍需要程序解析和校验。

| 校验层 | 要回答的问题 | Go 实现方向 |
| --- | --- | --- |
| 语法 | 是完整且唯一的 JSON 吗？ | `encoding/json` 解码，并检查后面没有第二个值 |
| 结构 | 字段、类型和必填项正确吗？ | 类型明确的结构体、未知字段拒绝、必填校验；必要时额外检查重复字段 |
| 业务 | 数量合理、商品存在、符合原输入吗？ | 独立业务校验，对照输入和可信数据 |

例如数量限定 1–100，JSON 中的 1000 即使可解析也必须拒绝。`true`、`"3"` 和缺失数量不能悄悄转换成合法订单。`DisallowUnknownFields` 能拒绝多余字段，却不会自动拒绝重复键或完成业务校验；当前工具参数解析可作为边界处理的参考。

## 结果格式与行动协议

结构化输出用于把结果交给程序；工具调用用于请求应用执行能力，还包括调用 ID、执行和回填。两者都可能包含 JSON，却有不同用途。字段类型合法不代表用户已授权写订单或转账。

遇到截断不要补括号后当作正确数据。字段缺失应报告明确状态或询问用户，不发明关键值。若设计修复请求，限制次数并算作新的模型调用；模型协议完成和业务验收通过分别记录。

## 后续练习与通过标准

1. 先写纯 Go 解析函数，以表驱动测试覆盖合法数量、越界、布尔、字符串、缺失、额外和重复字段。
2. 明确定义“不知道数量”的结构，不让零值掩盖缺失。
3. 再按模型服务当时支持的协议接入输出约束，新增接口、页面和观测；不要将未实现参数直接塞入现有接口。
4. 检查业务拒绝时根 span 的失败状态，区分模型成功与业务失败。

通过标准：能分别定位语法、结构、业务错误；所有输入通过应用校验后才进入业务操作。
