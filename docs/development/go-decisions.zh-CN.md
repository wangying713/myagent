# 本项目 Go 具体约定

本文件记录项目自己的工程约定，是对 Google Go 规范的补充，不代表 Google 官方规则。核心原则、具体语言规则和辅助建议的层级仍按 [规范阅读顺序](README.md#go-规范阅读顺序) 执行。

## 导入分组与顺序

手写 Go 文件的 `import` 按以下顺序分为三组，组间空一行：

1. **标准库（系统）**：Go 标准库，例如 `context`、`net/http`、`time`。
2. **本项目包（本地）**：当前模块 `saklay/ai` 及其子包，例如 `saklay/ai/apps/config`、`saklay/ai/domain/agent`。
3. **外部依赖（第三方）**：当前模块以外的依赖，例如 `github.com/gin-gonic/gin`、`go.opentelemetry.io/otel/trace`。Go 官方维护但不属于标准库的模块，例如 `golang.org/x/sync`，也属于这一组。

```go
import (
	"context"
	"net/http"
	"time"

	"saklay/ai/apps/config"
	"saklay/ai/domain/agent"

	"github.com/gin-gonic/gin"
)
```

- 没有导入项的组直接省略，不保留空组；只有一个导入项时可使用单行 `import`。
- 组内按导入路径排序，交给 `gofmt` 处理；保留确有必要的导入别名，不根据别名或业务功能再拆组。
- `gofmt` 会保留组间空行，不会自动按上述类别重新分组，添加导入时需要确认分组和顺序。
- 工具生成的文件沿用生成器输出，不手工修改 `.pb.go` 等生成文件的导入分组。

“标准库 → 本项目包 → 外部依赖”是本项目统一选择的顺序。Google 规范中的一般导入要求见 [Google Go 具体规范：导入](google-go-decisions.zh-CN.md#三导入)。

## 注释位置与简洁性

### 术语与判断顺序

这里按注释的位置区分两种写法，均使用 `//`：

- **独立注释**：独占一行或多行，紧邻对应声明的上方。
- **行尾注释**：与被说明的代码写在同一行，放在代码之后。

“注释内容只有一行”不代表应该使用行尾注释。手写 Go 代码（包括测试）先按声明类型和是否成组确定位置，再按信息量决定是否需要独立说明。

| 被说明的对象 | 注释位置 | 判断要点 |
| --- | --- | --- |
| 包、结构体及其他类型的用途 | 声明上方的独立注释 | 类型用途与字段含义分别说明 |
| 函数、方法，包括接口方法 | 声明上方的独立注释 | 即使说明很短，也不放在方法签名行尾 |
| 独立的一条 `const` 或 `var` 声明 | 声明上方的独立注释 | 即使说明很短，也独占一行；仅含一项的括号声明同样处理 |
| 成组 `const`、`var` 中的各项 | 简短说明放行尾，较多说明放该项上方 | 同组各项可按各自说明的信息量选择位置 |
| 结构体字段，包括匿名结构体和测试字段 | 简短说明放行尾，较多说明放字段上方 | 只有一个字段时也遵循字段规则 |

分组依据职责与语义；不要为了使用行尾注释，把独立声明硬凑成一组。结构体类型的用途说明放在上方，不随字段注释移动到类型声明行尾。

### 说明内容与长度

- 简短说明通常只解释一个含义，适合与代码同行阅读。内容较多、包含多项条件或约束，或与代码挤在一起影响阅读时，改用独立注释。
- 独立注释可按完整意思写成一行，也可按约束和段落分成多行；不强行合并成长行，不设固定字符数或代码行宽阈值。
- 包、类型、函数、方法及独立声明的文档注释通常以对应标识符名称开头；行尾注释直接说明含义，省略重复的标识符及“表示”“标识”“是”等引导词。对齐交给 `gofmt`。
- 移动或精简注释时保留原有含义，尤其不能删掉单位、nil 和零值语义、取消、并发、资源释放及部分结果等约束。
- 编译指令（如 `//go:embed`）和工具读取的注释保持所需位置与格式；生成文件不手改，`old` 历史归档不纳入整改。

### 示例

独立声明，即使说明很短也使用上方的独立注释：

```go
// MaxQuestionChars 是单个问题允许的最大 Unicode 字符数。
const MaxQuestionChars = 4096
```

成组声明中，各项的简短说明放在行尾：

```go
const (
	RoleSystem = "system" // 系统提示消息。
	RoleUser   = "user"   // 用户输入消息。
)
```

接口方法与普通函数、方法一样，说明独立放在声明上方：

```go
// ChatClient 提供业务需要的模型调用能力。
type ChatClient interface {
	// Chat 执行一次模型请求，并响应上下文取消。
	Chat(ctx context.Context, req Request) (*Response, error)
}
```

结构体的用途说明放在上方；字段说明较多时也独立放在字段上方：

```go
// Message 保存对话消息及可选的原始 JSON。
type Message struct {
	Role string // 消息角色。
	// Raw 保存完整的 assistant JSON，非空时优先用于编码。
	// 原始内容用于保留扩展字段和 null，不能用重组后的字段替代。
	Raw json.RawMessage
}
```

这是项目自己的注释位置约定；函数和类型等声明仍遵循 [注释和文档规范](google-go-decisions.zh-CN.md#二注释和文档)。

## 结构体字段说明

- 手写 Go 结构体的字段统一补充中文注释，包括导出数据、内部辅助类型、匿名结构体和测试数据；生成文件与 `old` 历史归档沿用原有内容。
- 字段注释说明具体含义，按需写明时间与大小单位、计数范围、nil 或零值语义、并发保护及关联关系；不只重复字段名称或 Go 类型。
- 简短说明放在字段行尾；内容较多或包含多项约束的说明放在字段上方，可写成一行或多行 `//`。具名结构体的用途说明放在类型声明上方，空结构体不添加无意义的字段说明。
- 同一行声明的多个字段可以共用能明确对应各字段的说明；含义不同、需要分别解释时拆成独立字段声明，保持字段顺序与类型不变。

```go
// ChatRsp 保存本次业务执行的结果。
type ChatRsp struct {
	Completed bool  // 本次业务是否成功完成。
	ElapsedMS int64 // 本次运行耗时，单位为毫秒。
}
```

这是为项目学习用途补充的说明约定，不是 Google Go 对所有字段的通用强制要求。

## 函数与方法参数数量

- 手写 Go 函数和方法的参数**最多 4 个，不得达到 5 个**。接口方法、函数类型、匿名函数及测试辅助函数同样遵循；生成文件和 `old` 历史归档不手改。
- 按实际参数个数计算：`ctx` 算一个，`question, prompt string` 算两个，可变参数 `args ...string` 算一个；方法接收者、泛型类型参数和返回值不计入。
- 参数达到 5 个时，先看是否把多件事放进了同一个函数；职责合理时，把相关输入合并为具名结构体。调用处写明字段名，让读者直接看出每个值的用途。
- `context.Context` 仍单独作为首参；同一次操作要用的模型、工具等依赖也可以放进输入结构体，通过具名字段明确传入。不把无关数据塞进大结构体，不通过全局变量、`map[string]any` 或可变参数绕过数量限制。
- 实现标准库、第三方接口或使用其规定的回调签名时，按外部要求保留签名；只有确实需要匹配外部约定时才适用此例外。

例如对话将问题、提示词、工具策略和单次预算放在请求里，模型客户端和默认预算由 `Client` 提供，调用时只传 `ctx` 和这份输入：

```go
// ChatReq 保存普通问答和工具对话的业务输入。
type ChatReq struct {
	Operation  string // 本次业务标识。
	Tools      Tools  // 可选工具，不提供时禁止调用。
	ToolChoice string // auto 允许模型选择，none 禁止调用。
	Question   string // 调用方提供的问题，不能为空或只有空白。
	Prompt     string // 调用方提供的提示词；为空时不添加系统消息。
	Limits     Limits // 全零使用客户端默认预算，覆盖时各值须为正数。
}

// Chat 统一处理普通问答和工具对话，并记录和汇总结果。
func (c *Client) Chat(ctx context.Context, req ChatReq) (ChatRsp, error)
```

示例问题和提示词由具体 API 或 Demo 调用方准备，通用 `Client.Chat` 不内置课程内容。普通聊天不提供工具；需要工具时传入工具集，`ToolChoice` 可用 `auto` 或 `none` 指定允许或禁止。禁用时，即使模型返回工具调用也会拒绝执行。

这是本项目为方便阅读设定的数量限制，不是 Google Go 的通用要求；分组思路见 [函数参数与可选配置](google-go-best-practices.zh-CN.md#六函数参数与可选配置)。

## 函数与方法行数

- 新增或修改的手写 Go 函数和方法**最多 90 行**；匿名函数、测试函数和测试辅助函数同样遵循。生成文件、第三方代码和 `old` 历史归档不手改。
- 按 `gofmt` 后的实际源码行数计算：从函数签名所在行到函数体结束大括号所在行，两端都计入，包含内部空行、注释、嵌套代码及匿名函数；声明上方的文档注释不计。嵌套匿名函数也单独检查，不能用它绕过外层行数限制。
- 接近或超过上限时，按实际职责拆分，例如参数准备、消息构造和执行过程。函数名应能说明拆出的步骤，不新增没有实际作用的转发层，也不为满足行数引入无关结构体或接口。
- 不通过压缩代码块、合并语句、挤在一行初始化字段，或删除必要注释、空行来凑行数；继续遵循代码块与复合字面量换行规则。
- 存量超限函数在后续涉及该函数时按职责治理；本规则不要求在无关任务中重写整个仓库。

90 行是本项目的可读性限制，不是 Google Go 的官方硬性要求。

## 请求参数命名

- 函数、方法只有一个业务请求或执行输入对象时，参数统一命名为 `req`；例如 `Chat(ctx context.Context, req ChatReq)`、`Chat(ctx context.Context, req Request)`。
- `ctx` 仍单独作为首参；另有模型、工具等依赖参数时，唯一的业务请求参数仍叫 `req`。领域方法、接口声明、模型与工具实现、相关测试替身和回调保持一致。
- 这项约定针对请求或执行输入对象。配置仍可叫 `cfg`，响应叫 `rsp`，依赖及普通辅助值按含义命名，例如 `tools`、`question`、`timeout`、`err`；只有 `ctx` 的方法仍使用 `ctx`。同一函数里的 HTTP 请求和业务请求需要区分时，HTTP 请求使用 `httpReq`。
- 只统一参数变量名，不因此修改 `MessagesInput`、`ChatReq` 等已有类型名，不把多个含义不同的输入硬合并。生成文件和 `old` 历史归档不手改。

这是本项目的命名偏好，目的是让同类方法使用相同写法，不是 Google Go 对所有单参数函数的要求。

## 客户端变量命名

- 手写 Go 代码中的客户端字段、函数参数和局部变量，统一使用“用途或服务名 + `Cli`”，测试代码及测试替身同样遵循。例如 Agent 客户端用 `agentCli`，对话客户端用 `chatCli`，明确按提供方区分时用 `deepseekCli`，HTTP 客户端用 `httpCli`。
- 按当前作用选择前缀；同一用途的字段、构造参数和调用处保持一致，例如 `newImplAgent(agentCli *agent.Client)` 将参数保存到 `agentCli` 字段。避免使用含义笼统的 `client`、`cli`，或混用 `chatClient` 与 `chatCli`。
- 导出字段仍以大写字母开头，如 `ChatCli ChatClient`。客户端依赖即使通过接口、包装器或测试替身提供，也按实际用途使用 `Cli`，例如 `Client` 和运行记录中的 `chatCli`。
- 这项规则针对客户端实例和依赖，不修改类型名 `Client`、`ChatClient`、`StreamClient`，构造函数继续用 `NewClient` 等原有名称。模型名称、配置及观测元数据仍按含义命名，例如 `Request.Model`、`Settings.Model`、`RunInput.Tools`；不将普通数据字段机械改成客户端名称。
- 范围为本项目手写 Go 代码及测试；生成文件、第三方代码和 `old` 历史归档不手改，前端命名另按前端规范处理。

```go
// ImplAgent 把 HTTP 请求交给 Agent 客户端处理。
type ImplAgent struct {
	agentCli *agent.Client // 由入口传入的 Agent 客户端。
}

func newImplAgent(agentCli *agent.Client) *ImplAgent {
	return &ImplAgent{
		agentCli: agentCli,
	}
}
```

这是本项目按个人阅读习惯统一的变量命名，不是 Go 对所有客户端的通用强制要求。

## 代码块与语句换行

- 手写 Go 代码（包括测试）的非空代码块统一展开：左花括号后换行，块内每条语句单独一行，右花括号另起一行；即使只有一条语句，也不压成单行。
- 函数、方法、匿名函数以及 `if`、`for`、`switch`、`select` 等代码块均遵循此规则，包括 `defer`、`go`、排序回调和测试回调中的匿名函数。`case`、`default` 后的语句也另起一行，不用分号把多条语句挤在一行。
- `if`、`for`、`switch` 头部所需的分号保留惯用写法，例如 `if err := validate(input); err != nil {`；空代码块可以保留 `{}`。生成文件与 `old` 历史归档不纳入整改。
- 换行只调整书写方式，保留原有求值时机与执行顺序。例如下面的闭包需要在函数返回时读取最终的 `err`，不能为了简写替换成 `defer execution.end(err)`。

```go
defer func() {
	execution.end(err)
}()

go func() {
	handler.ServeHTTP(w, req)
	close(done)
}()
```

这是项目自己的可读性约定，缩进和其他格式交给 `gofmt`。

## 复合字面量换行

- 手写 Go 代码（包括测试）中的非空结构体字面量统一采用多行写法，每个字段独占一行；即使只有一个字段，也不能将初始化压在同一行。该规则同样适用于指针初始化、函数参数、返回值及匿名、嵌套结构体。
- 切片、数组和映射的复合字面量包含多个元素时，每个元素独占一行；不因内容较短而挤在同一行。
- 左花括号后换行，最后一项保留尾逗号，右花括号另起一行；缩进和字段对齐交给 `gofmt`。
- 嵌套字面量逐层遵循同一规则；内层展开后，外层即使只有一个元素或字段，也展开书写，保持层次清晰。
- 空字面量可以保留单行，例如 `ImplAgent{}`。切片、数组和映射仅含一个简单元素时也可保留单行；这个例外不适用于非空结构体。字符串中的 JSON 等协议样本不按 Go 字面量拆分；生成文件（如 `.pb.go`）沿用生成器输出，第三方代码和 `old` 历史归档不纳入整改。

```go
questions := []string{
	FirstQuestion,
	SecondQuestion,
}

message := Message{
	Role:    RoleUser,
	Content: question,
}

impl := &ImplAgent{
	agentCli: agentCli,
}
```

这是项目自己的可读性约定，不是 Google Go 的固定行宽要求。

## 具名常量与字面量

- 业务操作标识、消息角色、结束原因、步骤类型、工具名称等固定取值，应在所属业务或协议包定义具名常量；同一含义在多处引用时必须复用定义，避免散落 `"messages"`、`"stop"` 等魔法字符串。
- 业务阈值使用表达含义的具名常量；可配置的默认值集中由所属包提供，例如问题长度用 `agent.MaxQuestionChars`，预算默认值复用 `agent.DefaultLimits()` 的字段，校验、配置和提示保持一致。
- 常量按职责就近分组，名称使用 Go 驼峰；跨包协议需要的定义可导出，局部实现细节保持私有。不为了收集常量新建全局 `common/constants` 包，也不因字符串取值相同就混用不同概念，如业务操作、服务名称与观测操作。
- 个别字面量可以保留：空串、直观的 0/1 和索引、局部结构的固定数量、只出现一次且语义明确的文案或局部值，以及 JSON 标签、JSON Schema、显式路由等协议声明。是否提取以含义、复用和维护成本判断，不要求消除所有字面量。
- 测试中的独立协议样本、边界输入和预期值可保留字面量，以验证线上取值不变；不要把所有预期都改成生产常量，导致常量改错时测试也同步放行。生成文件继续交给生成器处理。

例如 `NewChatRsp(OperationMessages)` 表达消息历史操作；其他包引用该标识时使用 `agent.OperationMessages`。这项约定是项目工程选择，不能据此把每个字符串、每个数字都视为错误。

## HTTP API 方法签名

HTTP 顶层只保留 `main.go` 一个 Go 文件，负责参数、配置、信号与最终错误输出。服务实现和测试放在 `http/app`（包名 `app`），启动入口为 `Run(ctx, cfg)`，由 `app/run.go` 组装依赖并管理资源。Agent 的处理方法、请求准备和各接口的 HTTP 响应组装位于 `http/app/impl_agent.go`，HTTP JSON 适配与错误映射位于 `http/app/handler.go`；后续业务使用 `app/impl_xxx.go`。API 的手写请求、响应、公共外层及共用 JSON 数据统一放在 `http/entity`，按业务分文件。路由与中间件位于 `app/router.go`，服务生命周期位于 `app/server.go`，通用传输能力留在 `infra/httpx`。

后续新增接口继续遵循这一分工：请求、响应和共用数据放在 `entity` 中，按业务分文件，各接口独立定义响应，按需复用步骤、用量等类型。`entity` 只负责字段和 JSON 标签，不依赖业务处理包、领域服务、Gin 或基础设施；请求准备和响应组装放在对应业务的 `app/impl_xxx.go`；HTTP 解码和错误映射位于 `app/handler.go`。领域层与 `infra/httpx` 不依赖应用的 `entity` 包。具体见 [HTTP 共用数据规范](../../apps/interfaces/http/entity/README.md)。

业务 API 统一使用 `(ctx, req) → (rsp, err)`：`context.Context` 和 `entity` 中手写的请求结构体指针作为入参，响应结构体指针与 `error` 作为返回值。

```go
func (a *ImplAgent) Chat(ctx context.Context, req *entity.ChatReq) (*entity.ChatRsp, error)
```

- API 方法负责参数转换、调用领域服务和返回结果，不接收 `gin.Context`，不解析 HTTP 或直接写出响应。
- `app/router.go` 逐条声明完整路径，通过 `handle(implAgent.Chat)` 这类单参数调用绑定具体方法；不通过反射扫描方法或解析注释生成路由。
- 解码、超时、取消及响应处理由 `http/app/handler.go` 集中完成。路由初始化通过 `requestTimeout(timeout)` 中间件显式设置当前路由的超时，计时仍从解码完成后开始；配置不放入全局变量。`infra/httpx` 只保留独立的严格解析、传输错误和 JSON 写出，不依赖业务或 `entity`。
- 接口方法显式组装并返回自己的 HTTP 响应，允许重复字段赋值，不封装统一业务返回函数。输入拒绝返回 nil 数据，其他失败保留已经完成的结果，错误原样返回。
- 响应和错误可以同时非空，已有的步骤和用量必须保留，不能因错误而统一丢弃响应。
- 业务执行、模型调用、工具执行和配置加载等需要表达“无结果”的对象使用指针：前置校验或准备失败返回 `nil, err`；已经开始执行并取得数据时，保留已有结果和错误。HTTP 实现根据结果是否为 nil 决定是否组装 data，不通过 `err != nil` 一律丢弃结果。模型响应保留实际请求、原始响应和流式片段，配置加载失败不返回半成品配置。
- 工具的正常业务拒绝保留非 nil 的 `OK=false` 结果；模型和工具返回 `nil, nil` 属于协议错误。数值、布尔和带明确存在标志的 `(value, ok)` 解析函数沿用值返回，不为形式统一引入指针。
- 领域层使用自己的输入输出，不依赖 HTTP 数据类型；JSON 解码直接保留省略切片为 nil、显式空数组为非 nil 空切片，可选数值用指针区分省略与零，不藏在上下文中。

请求消息统一使用 `Req` 后缀，响应消息使用 `Rsp` 后缀。三个 Agent 接口分别返回 `entity` 定义的 `ChatRsp`、`MessagesRsp`、`RunRsp`；业务方法不返回 HTTP 外层结构。

公共响应码常量定义在 `entity/code.go`，接口适配使用 `entity.CodeInvalidInput` 等具名常量。领域错误判断、HTTP 状态及具体提示保留在 `app/handler.go`，`entity` 不依赖领域或基础设施。

HTTP 统一外层手写于 `entity/response.go`：`Rsp[T]` 包含 `code`、`data`、`traceID`、`msg`。成功为 `code: "ok"`、`msg: "成功"`；失败沿用稳定的字符串错误码及中文说明，同时保留原有 HTTP 状态。解码失败、输入拒绝及其他尚无业务结果的响应使用 `data: null`，部分结果与错误同时返回时保留数据。HTTP handler 负责包装，`httpx.Write` 只编码并写出；编码失败不能先写出成功响应。

HTTP 入口在解码前使用官方 `otelgin` 中间件建立请求 span，显式注入私有 TracerProvider、noop MeterProvider 和空传播器，保持服务内链路且不依赖全局观测配置。领域运行作为其子 span，模型和工具仍是领域运行的子 span。通过 otelgin 的名称格式器只展示 URI 路由模板，例如 `/api/agent/chat`；未匹配路由统一为 `[unmatched]`。HTTP 方法保留在属性中，屏蔽默认属性中的原始路径、User-Agent 与客户端地址。启用正文采集时，在根 span 记录实际读写的请求体与最终 HTTP 响应，预览直接显示正文 JSON，不添加角色、消息或 body 包装；方法、路由模板和响应状态保留在 span 属性中，正文复用脱敏、限长及 OpenObserve 原生预览适配；不采集请求头或查询字符串，不预读请求。公共响应处理继续将 4xx 和 5xx 标记为失败。外层 `traceID` 来自实际请求链路，业务响应不再重复携带；关闭观测或服务退出闸门尚未进入路由时为空，不伪造 ID。

实现与使用说明见 [HTTP API](../../apps/interfaces/http/README.md) 和 [通用 HTTP 能力](../../infra/httpx/README.md)。

应用层 `app/agent_service.go` 在每次业务执行前通过具体的 `infra/openobserve.Client` 建立 `agent.run`，向领域客户端传入派生上下文，并在结束时记录结果。领域层只执行并返回原始回答、调用记录及 `RunInput` 中的实际输入，不定义观测接口，也不处理展示脱敏；`RunInput` 随结果保留已补齐默认值、通过校验的问题和实际工具、预算，观测层不重复推断。`infra/openobserve.Tools` 包装真实工具执行，模型观测仍由 DeepSeek 客户端负责。应用层只对返回展示副本脱敏，模型历史、工具结果和工作流后续输入始终使用原文。组合案例由应用层编排，每次独立业务执行各有自己的运行 span；流式案例在同步消费期间管理同一运行 span。`infra/openobserve` 组装输入与输出预览，保留采集开关、限长、部分结果及错误状态，不记录底层错误正文。

## 第三方能力选择

通用框架能力优先复用当前依赖，新增依赖须能减少维护成本并保留现有契约。HTTP 请求链路使用 `otelgin`，请求通过 `httpx.DecodeJSON` 按 JSON 标签严格解码，响应由 `encoding/json` 编码；保留已有字段检查及数字、零值、null 和空数组表现。

配置文件已使用 `godotenv.Read`。当前环境解析保留显式实现：显式空值优先于文件与默认值，布尔值仅接受规范化后的 true/false，整数沿用本机 int 范围。`caarlos0/env/v11` 的默认值与类型转换语义不同，当前规模下接入还需自定义解析及错误翻译，暂不增加该依赖。服务生命周期继续使用标准库，模型客户端保留原始 assistant 消息、取消与无重试语义。

## Agent Demos 与文本流式接口

经用户安排，`app/impl_agent_demos.go` 接入 13 个章节的最小演示，`entity/agent_demos.go` 分别手写各接口的请求、响应及共用 JSON 数据。原 API 独立保留。

普通 Demo 沿用 `(ctx, req) (rsp, error)` 和单参数 `handle`。文本流式接口的响应是同步拉取的 `iter.Seq2`，由专门的 SSE 适配写出；方法不依赖 Gin 或直接写 HTTP。每个事件沿用 `code/data/traceID/msg`，增量使用 `delta`，最终事件 `done=true` 并带完整或部分执行结果。流建立前失败返回普通 JSON；建立后失败用最终事件表达，不能再改 HTTP 状态。缺少最终事件视为中断。
