# Google Go 核心开发规范：中文译解

来源：[Google 官方核心规范](https://google.github.io/styleguide/go/guide)。作者为 Google；原文按 [CC BY 3.0 署名许可](https://creativecommons.org/licenses/by/3.0/)发布。本文件为中文整理译解，删减部分重复说明与外部示例，不是 Google 官方中文版本。

## 一、五项原则及优先顺序

可读的 Go 代码应满足以下原则，按重要程度排列：

1. **清晰**：读者能够理解代码的目的和这样写的原因。
2. **简单**：用尽可能简单的方式完成目标。
3. **简洁**：重要信息容易辨认，噪声较少。
4. **可维护**：后续修改容易做对。
5. **一致**：与周围代码和整个代码库保持一致。

遇到取舍时，后面的原则不能覆盖前面的原则。例如，为保持现有写法而让代码更难理解，并不符合规范。

## 二、清晰：从读者的角度考虑

清晰是可读性的核心。有效的命名、有帮助的注释、合理的代码组织共同帮助读者理解代码。**易读比易写更重要。**

### 让读者知道代码在做什么

当代码依赖读者事先知道某些背景时，应考虑：

- 使用更明确的名称。
- 补充必要的说明。
- 用空行或注释划分步骤。
- 拆分成职责明确的函数或方法。

没有一种写法能适用于所有场景。目标是让未来的读者更容易理解目的，而不是机械地缩短函数或增加注释。

### 让读者知道为什么这样做

名称能够解释意图时，让代码本身表达意图。名称解释不了的细节，需要注释，例如特殊的业务约束、语言行为、性能取舍和数学运算中的类型转换。

尤其要解释那些容易被维护者误改的内容。复杂实现若是为了性能，应说明原因和必须维持的约束；存在容易误用的接口时，应提供文档和用法示例。

注释也可能降低清晰度：重复代码的含义、与代码矛盾、写得过多，都增加阅读和维护负担。因此，优先解释**原因**，而不是逐句描述操作。

Go 标准库提供了很多可借鉴的例子：复杂算法的维护说明、能够运行的示例、通过小函数改善调用方可读性的设计。

## 三、简单：只引入必要的复杂度

简单代码应当：

- 能从上到下读懂，不要求读者记住大量前文。
- 没有不必要的抽象层。
- 值如何传递、决策在哪里发生，都容易看清。
- 提供独立可理解的文档、有用的错误和测试失败信息。
- 避免需要猜测才能理解的技巧性写法。

实现简单和调用简单有时会冲突。为了让调用者更容易正确使用接口，内部实现稍复杂可能值得；反过来，让调用者多做一点工作以保持实现清晰，也可能合理。

确实需要复杂度时，要有明确理由，例如性能要求或多个不同调用方的需求，并用注释、测试和示例说明正确用法。不要仅为未来可能出现的需求提前堆积复杂设计。

如果问题本来简单，实现却越来越复杂，应重新检查是否有更直接的方案。

### 使用最少的机制

表达同一个需求时，优先选择常见、标准的工具：

1. 能用语言基本结构完成，就使用通道、切片、映射、循环或结构体。
2. 基本结构不够，再找标准库，例如 HTTP 客户端或模板。
3. 原文在 Google 内部要求先检查已有核心库，再决定新增依赖或自行实现；应用到普通项目时，可理解为先检查项目已有的合适依赖。

例如，简单的集合成员判断通常可以使用 `map[string]bool`。只有需要更复杂的集合操作时，才考虑专门的集合库。

测试某项业务配置时，如果不是在测试命令行解析本身，通常直接设置配置值比通过命令行标志系统间接修改更简单。

## 四、简洁：突出重要的信息

简洁意味着信息密度高，不等于字符最少。重复代码、不透明的名称、不必要的语法和抽象、无助于结构的空白，都可能掩盖重点。

表驱动测试可以把共同执行逻辑集中起来，让各个用例的差异更明显。但表中应放真正变化的输入和预期，不要把每个步骤都做成复杂配置。

使用熟悉的惯用写法，能帮助读者快速识别目的：

```go
if err := validate(input); err != nil {
	return err
}
```

如果外观相似、行为却不同，应突出差异：

```go
if err := validate(input); err == nil { // 注意：这里处理校验成功的情况。
	use(input)
}
```

## 五、可维护：让未来的修改容易做对

代码被修改的次数远多于最初编写的次数。可维护代码应当：

- 容易正确修改。
- 接口能够合理扩展。
- 假设和边界清楚，抽象对应实际问题。
- 不包含无用功能和不必要的耦合。
- 有测试保护承诺的行为，失败时提供明确诊断。

接口会隐藏具体实现信息，这是能力，也有成本。只有收益足够时才引入接口，并明确说明行为契约，让维护者不用到处寻找实现才能知道如何调用。

不要把关键行为藏在一个容易忽略的字符或辅助函数里。例如，`=` 与 `:=` 的区别、复杂条件中的 `!`，可能直接改变含义。可以把赋值和错误判断拆开，让意图清楚：

```go
u, err := db.UserByID(userID)
if err != nil {
	return fmt.Errorf("查询用户: %w", err)
}
user = u
```

同一个概念在参数、接收者和不同方法中应使用可预测、稳定的名称。尽量减少依赖，尤其不要依赖其他包未公开、未承诺的内部行为。

选择结构时，应考虑以后如何扩展和修改。稍复杂但能够显著改善未来修改安全性的设计，有时是合理取舍。

## 六、一致：相同概念保持相同表达

一致性可以存在于一个文件、一个包、一个团队或整个代码库。相同问题反复使用不同方案、同一个概念反复换名称，都会增加阅读成本。

包内一致通常最直接影响读者。不过，一致性不能覆盖清晰、简单、简洁、可维护，也不能覆盖已有的明确规范。

## 七、核心规则

### 格式必须符合 gofmt

所有 Go 源文件都必须符合 `gofmt` 的输出。生成代码通常也应格式化，例如使用 `go/format` 包，方便阅读与检索。

### 多单词名称使用驼峰

标识符使用 `MixedCaps` 或 `mixedCaps`，不按其他语言的习惯写成下划线形式：

| 场景 | 推荐 | 不推荐 |
| --- | --- | --- |
| 导出常量 | `MaxLength` | `MAX_LENGTH` |
| 未导出常量 | `maxLength` | `max_length` |
| 局部变量 | `userCount` | `user_count` |

导出名称首字母大写；未导出名称和局部变量首字母小写。下划线的少数例外见[具体规范](google-go-decisions.zh-CN.md)。

### 不设固定代码行宽

Go 源代码没有固定行宽限制。感觉一行太长时，先考虑重构表达方式，而不是按某个列数强行拆行。如果已经足够简洁，可以保持长行。

不要仅为了行宽拆分长字符串或网址。不要在会导致读者混淆缩进层级的地方换行，例如函数声明或条件表达式进入代码块之前。

因此，“任何一行都不能超过 80、100 或 120 个字符”不是 Google Go 核心规范。

### 命名结合调用位置

Go 名称往往比其他语言短，但应做到：

- 使用时不显得重复。
- 考虑包名、类型和所在作用域提供的上下文。
- 不重复已经明确的信息。

例如 `http.Client` 比 `http.HTTPClient` 清楚；名称长短应服务理解。

### 局部一致性的边界

规范没有规定的风格，可以自行选择；附近代码已有一致做法时，通常沿用附近做法。

原文认可的局部选择包括用 `%s` 还是 `%v` 打印错误，以及在适合的情况下使用缓冲通道还是互斥锁。固定代码行宽和断言库不属于可以用局部一致性覆盖的事项。

如果现有偏差只影响一个文件，修复又超出本次改动范围，可以单独记录后续修复。若新代码会扩大偏差、把偏差暴露到更多接口、影响更多文件或引入实际错误，就不能再以“原来也是这样写的”为理由继续扩散。

可以在当前改动中清理、先重构再实现，或者选择至少不扩大问题的方案。规范更新本身也不意味着要对整个仓库进行一次大规模风格重写。
