# Google Go 最佳实践：中文重点译解

来源：[Google 官方最佳实践](https://google.github.io/styleguide/go/best-practices)。Google 原文采用 [CC BY 3.0 署名许可](https://creativecommons.org/licenses/by/3.0/)。本文件提炼常见场景的建议，省略大量重复例子，不是逐句全文翻译。

**这些是辅助建议，不等同于强制规范。** 应结合具体需求使用，并服从核心规范和具体规范。

## 一、名称表达动作与结果

取得某个值的方法通常使用名词式名称，例如 `JobName()`；执行动作的方法通常使用动词式名称，例如 `WriteDetail()`。不要重复接收者、包名或返回类型已经表达的信息。

多个函数只在处理类型上不同，可以把类型放在名称末尾，例如 `ParseInt` 与 `ParseInt64`。如果有明显的主要版本，主要版本可以省略类型后缀。

测试替身应准确说明是简化实现、桩、模拟对象还是记录调用的对象。跨包复用的辅助包可以使用生产包名加 `test` 的方式，但没有复用需求时不必专门建包。

避免内层变量遮蔽外层关键变量，尤其是 `err`。不要仅因为语法允许，就让读者难以判断后续代码使用哪一个值。

避免用一个 `util` 包收集所有零散代码。能归入具体职责的代码应放入对应包；无法描述职责，往往说明抽象边界还不清楚。

## 二、包和文件的大小

包应围绕一致的职责组织，让使用者容易理解它提供的能力。不要因为文件很长就把紧密耦合的功能拆成两个必须一起使用的包。

也不要把整个系统都塞进一个无法导航的大包。包的边界由职责、依赖和使用方式决定，不由固定的行数或文件数决定。

文件同样没有“一种类型必须对应一个文件”的硬性要求。相关声明放在一起通常更有帮助；避免大量只有一点内容的小文件，也避免很难浏览的超大文件。

生成的协议消息和服务桩，应使用调用方容易识别、能避免冲突的导入名称。导入排序和格式尽量交给工具。

## 三、错误应说明这一层发生了什么

### 选择合适的错误结构

- 调用者只需要知道失败原因时，普通错误字符串可能足够。
- 调用者需要识别某种预期情况时，可以提供稳定的哨兵错误。
- 调用者需要读取结构化信息时，可以定义实现 `error` 的具体错误类型。

不要为了每一个错误创建新类型，也不要让调用者通过拆解错误字符串决定业务行为。

### 添加上下文而不是堆叠同义词

包装错误应补充当前操作和有助于定位的信息，不要每层只加“失败”“错误”等没有新内容的前缀。

```go
return fmt.Errorf("读取配置 %q: %w", path, err)
```

错误信息的组合方式要考虑最终阅读顺序。`%w` 放在何处会影响可读性；通常先写这一层的背景，再放下层原因。不要把这种常见写法当成无法例外的格式模板。

### 包装会形成接口契约

使用 `%w` 保留底层错误链，调用者能够用 `errors.Is`、`errors.As` 识别。使用 `%v` 只保留文字描述，不暴露同样的链式识别能力。

是否暴露底层错误，应依据公共 API 契约决定。若底层存储实现以后会替换，直接让所有调用方依赖其私有错误类型，可能增加迁移成本。

因此，不要把“每个错误必须用 `%w` 包装”或“系统边界必须一律改成 `%v`”当成 Google 的绝对规则。

### 记录与处理

记录日志的层应有足够信息判断影响和处理方式。只记录而不采取必要行动，并不意味着错误已经被处理。

避免每层一边记录同一个错误一边原样返回，让一次失败产生很多重复日志。通常由更靠近请求或任务边界的一层集中记录；特殊诊断需求另行设计。

注意日志接收方是否适合存放敏感信息。不要无意把完整请求、令牌或用户数据放入错误文本和日志。

### 初始化与 panic

启动时发现无法继续的配置问题，可以由入口决定终止。普通库把错误返回给调用方，而不是自行结束整个进程。

程序检查用于发现内部不变量破坏，不能替代用户输入检查。合理使用 `panic` 的场景应确实是程序员无法按普通失败处理的情况，而不是数据库暂时不可用等常见故障。

## 四、文档写清楚调用者的责任

函数签名能够说明类型，却不能表达全部契约。文档应补充重要信息：

| 方面 | 需要说明的内容 |
| --- | --- |
| 参数 | 有效值、缺省行为、配置间的约束 |
| 上下文 | 取消是否会结束操作，特殊生命周期要求 |
| 并发 | 是否支持并发调用，调用方是否负责同步 |
| 清理 | 返回对象是否需要关闭，谁负责释放资源 |
| 错误 | 哪些错误可以被识别，失败后对象处于什么状态 |

普通的上下文参数不必在每个函数里重复解释所有通用知识，但不常见的取消行为必须说明。异步操作要说明启动、完成、错误通知和关闭的关系。

结构体的零值是否能使用、选项是否可以省略、失败是否有部分结果，也应让调用者知道。

文档应作为文档阅读，避免把所有说明塞在看不见的实现注释中。预览生成的文档，检查标题、链接、代码块和示例是否容易理解。

代码出现不常见但有意为之的写法时，用简短说明突出该差异，而不是要求读者猜到。

## 五、声明与初始化

非零初始值通常使用 `:=`；需要零值时，直接用 `var`，让意图清楚：

```go
var count int
var buffer bytes.Buffer
name := "默认配置"
```

不要无意义地写 `var count int = 0`。结构体零值可用时，不必为每个零值字段填一遍值。

需要修改映射时，使用 `make` 或映射字面量创建它；空切片可以保持 nil。需要特定序列化结果时，按契约创建非 nil 空切片。

知道实际大小或测量证明有收益时，可给切片、映射提供容量提示。不要猜测一个很大的容量，然后无条件为所有调用分配。

通道参数能明确方向时，使用 `<-chan T` 或 `chan<- T` 表达接收或发送能力，缩小误用空间。

## 六、函数参数与可选配置

函数输入很多时，先检查职责是否过大，或是否存在更合理的分组。可选参数较多时，考虑配置结构体或函数式选项，不规定统一的“超过几个参数就违规”。

### 配置结构体

适合多个调用者通常都需要设置较多选项的场景。字段应有清楚含义，默认值和非法组合需要说明。

不要把必需参数全部隐藏进一份巨大配置，也不要把 `context.Context` 塞进配置结构体。请求上下文仍作为显式参数传递。

### 函数式选项

适合大多数调用者使用默认值、少数调用者需要扩展选项的场景，例如 `WithTimeout`。调用处可以自然表达意图，也便于新增可选项。

代价是额外类型、函数和抽象。只有它比直接参数或配置结构更合适时才使用，不把它作为所有构造函数的必选模式。

## 七、命令行程序

简单命令使用标准工具往往足够。包含很多子命令的程序，可以考虑合适的命令行框架，但框架不能代替合理的业务边界。

命令行层负责解析输入、构造依赖、调用业务逻辑和决定退出状态；普通包提供可测试、可复用的逻辑。不要让整个业务接口依赖命令行库或全局标志。

## 八、测试实践

### 让测试函数决定是否失败

区分两种辅助代码：

- **环境辅助函数**：构建对象、生成数据、启动测试服务、清理资源。
- **校验逻辑**：比较结果，给出是否满足契约及差异。

环境辅助函数在准备失败时可以通过测试对象报错。领域校验逻辑优先返回结果或错误，由测试函数输出包含输入和上下文的失败信息，避免隐藏在自制断言系统里。

需要被多种实现复用的契约测试，可以围绕清楚的被测接口和测试入口组织，不应成为晦涩的“测试框架”。

### 合适时使用真实传输

测试关注网络协议、编码、请求传播或客户端与服务端协作时，真实传输层往往比直接调用内部方法更有意义。可以使用本地测试服务器，不一定需要远程服务。

只测试一个纯函数或处理分支时，则不必为了形式完整启动整套网络环境。选择对应被测行为的层次。

### t.Error 与 t.Fatal

后续验证仍有意义时，用 `t.Error` 或 `t.Errorf` 报告并继续。前置准备失败、结果不存在或继续执行会产生误导时，用 `t.Fatal` 或 `t.Fatalf` 停止当前测试。

测试辅助函数通过 `t.Helper()` 让失败位置指向调用方。准备和清理应尽量对称；可以让测试清理机制管理资源。

**不要从测试创建的其他协程调用 `t.Fatal`、`t.Fatalf` 或 `t.FailNow`。** 它们应在运行测试函数的协程中使用。后台协程把结果或错误发回测试协程，再由测试协程决定失败。

### 数据和环境隔离

结构体测试数据使用字段名，方便阅读、扩展与检查。每个测试只进行自己需要的准备，避免无关测试为共享初始化支付成本。

`TestMain` 适合真正属于整个测试程序的初始化与清理，不应成为所有测试必须经过的复杂流程。共享昂贵环境时，应确保用例之间的状态重置和隔离，不依赖执行顺序。

## 九、字符串拼接

| 情况 | 常见选择 |
| --- | --- |
| 少量简单字符串连接 | `+` |
| 混合值与格式表达 | `fmt.Sprintf` |
| 循环中逐步构造长字符串 | `strings.Builder` |
| 编译时已知内容 | 常量表达式 |

选择让内容和结构容易看懂的方式，性能关键处再用测量判断，不必把所有短字符串连接都改成构建器。

## 十、减少可变全局状态

包级可变状态可能使调用隐藏依赖、测试互相影响、并发行为不明确。尽量把依赖和配置放在对象实例或显式参数里。

可变全局状态的常见问题包括：谁负责初始化、初始化顺序是什么、失败怎么报告、是否允许运行时修改、多个测试是否能同时使用不同配置。

全局默认实例有时便于调用，但应保留创建独立实例的能力。默认实例不应阻止测试隔离、配置两个不同对象或注入不同依赖。

判断一个设计时，可以问：能否同时创建两个不同配置的实例？测试能否独立替换依赖？是否存在未说明的初始化顺序？若不能，应重新审视全局状态的必要性。

## 十一、设计有效的接口

不要在实现尚未稳定、调用需求还不清楚时，为每个类型预先定义接口。先让具体类型完成职责，在实际使用边界提取所需能力。

接口通常放在消费方。生产方返回具体类型，让不同消费方根据需要定义不同的小接口。协议型接口或多个实现共同遵循的公开契约可能例外，应明确理由。

接口应围绕真实行为，而不是把某个结构体的所有方法复制一遍。文档说明并发、所有权、清理和错误语义；方法签名相同并不自动意味着契约相同。

不要把复杂性推给调用者：需要频繁类型断言才能使用的接口，可能没有提供合适的抽象。对非导出接口，也应记录无法从签名看出的关键约束。

接口设计和包设计一起考虑。避免为了细小接口拆出很多不能独立理解的包。
