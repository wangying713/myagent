# Google Go 具体规范：中文重点译解

来源：[Google 官方具体规范](https://google.github.io/styleguide/go/decisions)。Google 原文采用 [CC BY 3.0 署名许可](https://creativecommons.org/licenses/by/3.0/)。本文件按主题提炼规则与理由，删减大量示例，不是逐句全文翻译。它从属于[核心规范](google-go-guide.zh-CN.md)。

## 一、命名

### 下划线的例外

Go 标识符通常不含下划线，主要例外是：

- 仅供生成代码导入的包名。
- `*_test.go` 中的测试、基准测试和示例函数名。
- 与操作系统或 cgo 交互的少量底层代码，需要沿用外部名称。

**文件名不是 Go 标识符**，可以使用下划线，例如 `user_service.go`。

### 包名

包名通常用简短的小写名称，不使用驼峰或下划线。名称应表达具体职责，避免 `util`、`common`、`helper` 等无法说明内容的泛化名称。

考虑调用方会看到的完整名称：`storage.Client` 已经包含包的上下文，不必再写成 `storage.StorageClient`。包名相同时，才考虑有意义的导入别名。

包名和目录名、导入路径是不同概念，不能仅凭路径末尾判断包名。需要兼顾包的职责、现有惯例和调用位置。

### 接收者、常量与缩写

- 方法接收者用简短的类型缩写，例如 `func (s *Server)`，不使用 `this` 或 `self`。
- 同一类型的方法保持接收者名称一致；接收者名称不必每次重复完整类型名。
- 常量按职责命名，仍用驼峰，不使用全大写下划线形式。
- 常见首字母缩写保持统一大小写，例如 `URL`、`HTTP`、`ID`；使用 `HTTPServer`、`userID`，避免 `HttpServer`、`userId`。

### 访问方法与变量

访问方法一般省略 `Get`：使用 `Name()`，而不是 `GetName()`。设置方法可以叫 `SetName()`。

局部变量名的长度与作用域、用途对应。短循环里的 `i`、常见上下文参数 `ctx`、错误变量 `err` 都可以清楚；长作用域和复杂业务应使用更明确的名称。

不要为了给每个变量配长名字而损失可读性，也不要在复杂业务中用无法解释的单字母名称。避免重复包名、类型或已有上下文，不把类型机械地编码进变量名。

## 二、注释和文档

文档注释应紧邻声明，并通常以被说明的标识符名称开头。包注释说明包提供什么能力、适用场景和重要约束，不是文件目录清单。

注释应当表达完整意思，适当使用句子和标点。正文注释可以适当换行以便阅读，但这不等于给代码设置固定行宽。

给导出接口提供示例时，优先使用可以被测试执行的 `ExampleXxx`，让示例和真实行为一起维护。代码示例应当可理解，不依赖读者从其他地方补齐大量背景。

命名返回值可以辅助文档，但不要为了省略 `return` 后的值而让读者必须回到函数签名猜测结果。较长函数里，明确写出返回值通常更清楚。

## 三、导入

- 需要消除冲突时才重命名导入；必要的生成代码导入别名应保持一致。
- 通常把标准库导入放在第一组，与其他导入用空行分隔。
- 不为了模仿其他语言而制造很多细碎的导入分组。
- 空白导入 `_ "包路径"` 用来引入初始化副作用；通常应集中在主程序或测试入口，避免库偷偷引入副作用。
- 点导入 `. "包路径"` 会隐藏名称的来源，应避免；原文存在为解决特定外部测试依赖问题而使用的少量特殊情况。

## 四、错误处理

### 用 error 表达失败

普通失败通过返回 `error` 表达，不依赖 `panic`，也不要把失败编码进正常结果，例如拿空字符串或 `-1` 充当错误。

多返回值中，`error` 通常放最后。若 API 使用 `(value, ok)` 表示“是否存在”，应明确其含义，不要让调用者猜测。

### 检查与处理错误

返回的错误需要被检查、处理或向上传递。不要把错误简单丢弃。确实可以忽略的情况，应使理由可见，而不是用 `_` 隐藏意外失败。

错误信息应有助于诊断。英文错误字符串通常不以大写字母开头、不以标点结尾；专有名称和缩写不能被机械地全部转为小写。中文没有大小写问题，仍应避免无意义的重复前缀和末尾标点。

不要仅为表达同一错误而逐层重复记录日志。包装错误时，应添加这一层独有的操作、参数或背景。

### 错误路径提前返回

先处理失败，让正常路径保持较少缩进：

```go
result, err := load(ctx, id)
if err != nil {
	return nil, fmt.Errorf("加载记录 %q: %w", id, err)
}
return result, nil
```

若 `if` 分支以 `return`、`break` 或 `continue` 结束，一般不再加无必要的 `else`。

## 五、字面量与声明

### 结构体字段和括号

结构体字面量优先使用字段名，特别是外部包类型、多字段结构和测试数据。少量非常简单、位置含义明显的内部结构存在例外，不应把所有情况机械地当成错误。

```go
cfg := Config{
	Address: ":8080",
	Timeout: 5 * time.Second,
}
```

依照 `gofmt` 组织括号和缩进。避免为了换行而让结束括号与控制流代码块的边界混在一起。嵌套字面量在类型已经明确时，可以省略重复的类型名。

省略没有额外意义的零值字段，除非显式写出零值能强调重要行为。

### nil 切片

声明空切片时，优先使用：

```go
var users []User
```

nil 切片与非 nil 的零长度切片大多数操作相同，长度都是零，也都可以 `append`。不要仅因为担心“未初始化”而禁止 nil 切片。

两者在序列化等场景可能不同。例如 JSON 中 nil 切片通常编码为 `null`，非 nil 空切片编码为 `[]`。需要哪个结果，应由接口契约决定。**nil 映射不能直接写入**，这一点与 nil 切片不同。

## 六、控制流与语言用法

### 条件、循环和函数签名

代码过长时，优先简化表达式、给重要业务条件命名，或调整接口。不要为了某个固定列数把条件拆到无法辨认代码块的程度。

表达同一种状态的多个分支，适合时使用 `switch`。保留逻辑的自然顺序，不为了形式统一把所有分支都变成同一种写法。

Go 的 `switch` 分支默认不会自动进入下一分支，通常不需要写 `break`。循环里嵌套 `switch` 时，`break` 作用于最内层可中断结构；需要退出外层循环时，明确使用标签或其他清楚的控制流。

### 避免不安全的复制

不要复制已经使用的互斥锁、等待组等同步对象。某些标准库结构也有复制限制，应检查其文档。

切片、映射等值的复制通常不会复制底层数据。审查共享状态时，要理解它们仍可能引用同一份数据。

### panic 与 Must 函数

不要对一般业务失败或可预期的输入错误使用 `panic`。不可恢复的程序不变量破坏，以及少量确定性初始化场景，可能有不同处理方式。

`MustXxx` 表示失败时会触发 `panic`，适合明确保证成功的初始化或测试辅助场景，不适合处理不可信请求、用户输入或随时可能失败的外部操作。

不要用 `recover` 把普通错误处理伪装成异常系统。

### 协程生命周期

启动协程之前，应明确：它何时结束、谁负责取消、谁等待它退出。不要启动一个既没有退出条件，也无法被调用方控制的后台协程。

通道发送、接收和等待都可能阻塞。应检查消费者提前退出、请求取消、服务关闭时，生产者能否结束；检查通道由谁关闭、是否可能重复关闭或关闭后发送。

可取消信号和退出等待解决不同问题：调用取消函数，并不等于协程已经退出。

### 优先同步函数

同步函数直接返回结果，并在返回前完成必要的回调或处理，调用者更容易管理生命周期、并发数量和错误。

需要异步时，调用者可以在外部启动协程。确实提供异步 API 时，应清楚说明完成、取消和错误通知机制。

## 七、接口、泛型与接收者

### 接口放在使用方

接口通常由需要调用能力的一方定义，包含实际需要的方法。实现方通常返回具体类型，而不是提前设计一个接口让所有消费者依赖。

不要仅因为“以后可能做替换”或“测试一定要有模拟对象”而为每个结构体配接口。优先考虑实际边界和调用需求，接口应尽量小而聚焦。

### 泛型解决真实重复

泛型可以消除真正重复的、类型安全的算法或数据结构代码。若传统函数或小接口更简单，就使用它们。

不要为了使用泛型扩大公共接口，也不要靠 `any` 和大量类型断言制造伪通用设计。泛型并不是规避测试、文档或清晰命名的理由。

### 值、指针与接收者

需要修改对象，或对象包含不能安全复制的字段时，使用指针。大型结构也可能适合指针；简单的小值、字符串、整数等通常按值传递。

映射、通道、函数本身通常按值传递，不需要再加一层指针。切片方法若只访问元素而不修改切片头，通常可以使用值接收者。

正确性优先于速度和形式。选择接收者时还应考虑方法集合、接口实现和未来的维护，避免随意混用而造成调用差异。不应把某个字节数当成普遍的强制分界线。

### 类型别名、字符串与 any

类型别名主要用于迁移、兼容等明确需求，不应成为掩盖包边界的常用手段。

打印需要区分边界的字符串时，使用 `%q`，让空格、空字符串和控制字符更容易被看见。

项目支持 Go 1.18 及以上时，优先使用 `any` 表达空接口类型，而不是反复写 `interface{}`。

## 八、常用库与上下文

### 配置和日志

命令行标志属于程序入口。普通库应通过参数、配置或对象接收需求，避免把业务逻辑绑定到进程级标志。

Google 的日志部分涉及其内部日志设施，应保留“选用适合项目的日志方案、明确级别和处理位置”的原则，不能直接把内部包路径当成普通项目应安装的依赖。

### context.Context

上下文应沿调用链显式传递，用于截止时间、取消和请求相关信息。接收上下文的函数和方法，把 `context.Context` 放在第一个参数位置，通常命名 `ctx`。

```go
func Fetch(ctx context.Context, id string) (*Record, error)
```

HTTP 处理函数从 `req.Context()` 获得上下文；流式 RPC 从流对象获得；程序入口可以创建基础上下文。调用链中间的库代码通常应接收调用方的上下文，而不是自行创建 `context.Background()`，否则会切断取消和请求信息的传递。

不把请求上下文存进结构体或选项结构，改为在需要的方法参数里显式传递。必须匹配外部接口签名的少数情况需要专门设计。

不定义替代 `context.Context` 的自制上下文接口；业务参数通过普通参数、接收者或确实适合的上下文值传递。

原文说明 Go 1.24 增加测试上下文 API，支持它的项目可以从测试对象获取上下文。使用新 API 前，仍需核对项目的 Go 版本，不能仅凭文档较新就升级工具链。

### 随机数

安全敏感的随机值使用 `crypto/rand`，例如令牌、密钥相关随机材料。不要用非密码学随机源生成需要不可预测性的值。

## 九、让测试失败信息有用

读者应尽量不打开测试源文件，就能知道：哪个操作失败、输入是什么、实际结果是什么、预期是什么。

### 比较与错误报告

Google 倾向使用 Go 本身表达条件与失败报告，避免断言库或自制断言语言把比较和报错信息藏起来。复杂对象可以使用 `go-cmp` 等比较工具，注意它与泛化断言框架不是同一类工具。

先写实际结果，再写预期结果。中文测试提示也保留这个顺序：

```go
got := Add(2, 3)
if got != 5 {
	t.Errorf("Add(2, 3) 实际为 %d，预期为 5", got)
}
```

完整结构比较通常比一条条遗漏字段更有帮助。根据契约忽略时间戳、随机标识等非稳定字段；不要依靠字符串格式化结果来判断对象相等。

需要差异报告时，说明差异的方向与含义。错误测试关注是否失败、错误类型或可识别语义，通常不比对完整错误字符串，除非字符串本身就是 API 契约。

### 继续报告与停止测试

后续检查还有效时，可以继续报告多个失败。前置条件不成立、继续执行会导致无意义结果或崩溃时，使用致命失败停止当前测试。

不要把每个检查都做成第一次不符合就立即退出的断言，否则容易丢失诊断信息。

## 十、测试结构

### 子测试和表驱动

多个场景共享执行步骤时，表驱动测试可以减少重复。表中放真正变化的数据，不要塞入大量布尔开关、行为函数和难以理解的配置。

每个用例需要容易定位的名称，适合时使用 `t.Run`。子测试名称在 `go test -run` 中具有筛选意义，避免无意使用 `/` 造成层级变化。

不同场景的执行逻辑已经显著不同，就分成独立测试或子测试，不要强行塞进一张表。

### 测试辅助函数

用辅助函数处理环境构建、数据生成和清理。需要将失败归因到调用位置时，使用 `t.Helper()`。

领域校验逻辑优先返回值、差异或错误，让测试函数决定如何报错，而不是在辅助函数内隐藏所有断言。

### 测试包的选择

- 同包测试能访问未导出符号，适合验证包内部实现。
- 外部测试包，例如 `storage_test`，能从调用者视角验证公开 API。

根据目的选择，不机械地要求所有测试都在同一侧。Go 原生测试以 `testing` 包为基础。

## 十一、没有规定的事项

这不是所有风格问题的穷尽清单。原文没有规定的事项，应根据清晰、简单和局部一致性判断，不应把个人喜好包装成 Google 的强制要求，也不必为了无关风格差异阻塞一次有效改动。
