# Go 并发与上下文

这是根据 Google 的协程、同步函数和上下文规范编写的中文适配草案，主题参考社区并发与上下文技能。来源见[说明](../../sources.zh-CN.md)。

按需阅读[具体规范中的协程和上下文](../../google-go-decisions.zh-CN.md)，以及[最佳实践中的并发文档与接口](../../google-go-best-practices.zh-CN.md)。

## 先明确生命周期

启动每个协程之前，明确它的必要性、负责人、停止信号、退出条件、错误传递和等待方式。函数可以同步完成时，优先让调用者决定是否并发执行。

区分取消与完成：取消只是信号，不代表操作已经结束。关闭服务或测试清理时，需要等待相应任务退出。

## 上下文传播

- `context.Context` 通过参数沿请求调用链传递，通常为第一个参数 `ctx`。
- HTTP 入口使用请求上下文，数据库和外部调用使用能接收上下文的接口。
- 不在调用链中间随意创建 `context.Background()` 切断取消与截止时间。
- 不把请求上下文存入普通结构体或可选配置，不定义替代它的自制上下文接口。
- 创建带取消、超时或截止时间的子上下文后，在所有正常控制路径释放取消资源，除非责任明确移交。
- 业务必需参数显式传递；上下文值只携带适合请求范围的元数据。
- 需要脱离请求继续执行的工作必须有独立责任、期限和关闭机制，不因使用脱离取消的上下文就成为无限后台任务。

## 通道与共享状态

- 明确谁发送、谁接收、谁有权关闭；多个发送者存在时，由能确定所有发送已结束的一方协调关闭。
- 在接口中用通道方向限制能力，检查关闭后发送、重复关闭和无消费者的发送。
- 通道等待可能阻塞时，检查取消或完成如何解除阻塞；不机械地要求每个 `select` 都有相同分支。
- 通道传递指针本身不是错误，但必须检查对象所有权、后续修改和并发访问。
- 缓冲大小与并发数量需要明确边界，不能靠无限启动协程掩盖吞吐不足。
- 共享可变状态使用适合的同步方式。切片和映射赋值不会自动深复制底层数据。
- 不复制已使用的互斥锁、等待组等同步对象；检查锁顺序和持锁等待是否可能形成死锁。

通道适合传递数据和协调，互斥锁适合保护共享状态。根据模型和清晰度选择，不把其中一种定为全局唯一方案，也不因“读多写少”就自动替换成 `sync.Map`。

## 验证

检查正常完成、调用方取消、超时、生产者失败、消费者提前退出和服务关闭等路径。根据实际实现选择竞态检测、可控阻塞测试与退出检查。

验证必须同时关注停止信号和最终退出，不能只断言调用了取消函数。不为评审自动安装协程检测库或升级工具链；需要新增依赖时先结合项目现状判断。

用中文交付发现、影响及证据，区分实际竞态或死锁与仅需要说明的设计取舍。
