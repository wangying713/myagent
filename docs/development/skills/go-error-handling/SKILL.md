# Go 错误处理

这是中文适配草案。主要依据 Google 规范，主题分类参考社区错误处理技能，**不是上游技能的完整翻译**。来源见[说明](../../sources.zh-CN.md)。

按需阅读[具体规范中的错误处理](../../google-go-decisions.zh-CN.md)与[最佳实践中的错误设计](../../google-go-best-practices.zh-CN.md)。

## 检查重点

- 预期失败通过返回 `error` 表达，返回值最后放错误；检查错误是否被处理或向上传递。
- 忽略错误需要可理解的理由，不能隐藏会影响后续正确性的失败。
- 新增错误信息补充这一层独有的操作和参数，避免只重复“失败”。
- 使用 `%w` 会向调用者暴露可识别的底层错误链；根据 API 契约决定是否包装，不机械地每层包装或在边界全部抹除。
- 已包装的错误需要匹配哨兵或类型时，使用适合的 `errors.Is`、`errors.As`，不要仅比较完整字符串。
- 哨兵错误用于稳定可识别的条件；自定义类型用于需要携带数据的错误；普通文字足够时保持简单。
- 普通业务失败不用 `panic`。`MustXxx` 只用于明确接受失败即中断的场景。
- 同一错误的记录应有明确责任层，避免每层记录后原样返回导致重复日志。
- 面向用户的响应与内部诊断根据接口设计处理；错误和日志不无意泄漏敏感值。

英文错误信息通常不以大写或末尾标点装饰，但专有名称和缩写存在例外。中文错误信息保持清楚、可组合，不套用英文大小写规则。

## 示例

```go
record, err := store.Load(ctx, id)
if err != nil {
	return nil, fmt.Errorf("加载记录 %q: %w", id, err)
}
return record, nil
```

这个例子适用于需要保留底层错误链的接口。是否在此处记录日志，应根据上层处理责任决定，不因为返回错误就额外记录一条相同日志。

## 验证与交付

检查真实失败路径、包装后是否仍能识别约定错误、是否重复记录以及调用方行为。已有相关测试时运行受影响的测试；修改错误语义时补充必要的行为验证。

不强制新增第三方错误库或日志库，不自动升级 Go 版本。用中文说明错误如何传播、由谁处理，以及公共错误契约是否改变。
