# 06：失败、预算、重试与权限

## 先把错误分清楚

| 错误层 | 例子 | 合理的动作 |
|---|---|---|
| 配置 | 没填密钥、端点不正确 | 在调用前修正配置 |
| 网络/HTTP | 超时、鉴权失败、限流、服务端异常 | 判断是否临时故障；不要一律重试 |
| 模型协议 | 非 JSON、缺少 message、输出截断 | 保留响应证据，报告未完成 |
| 工具输入 | 未注册工具、参数类型错误 | 不执行，返回明确工具错误 |
| 工具执行 | 查不到记录、下游故障 | 返回实际结果，不虚构成功 |
| 业务验收 | JSON 合法，但数量超出范围 | 由业务层拒绝或补充确认 |
| 观测 | OpenObserve 不可用 | 一次性提示，模型运行继续，之后检查入库 |

客户端目前不会自动重试。首次学习时，这使“一次调用发生了几次实际请求”非常明确。服务状态码解释可查阅 [DeepSeek 错误码](https://api-docs.deepseek.com/quick_start/error_codes)。

## 预算有四种，不要混在一起

**轮次预算**限制模型最多被调用几次。**工具次数预算**限制真正执行的动作数。**token 预算**约束累计开销。**时间预算**约束用户等待时间。

当前示例中：最多 5 次模型调用、8 次工具执行；每次默认 `max_tokens=512`；在下一轮调用前检查累计已知 token 是否达到 8000；HTTP 操作默认超时 60 秒、连接超时 10 秒。

累计 token 是**软预算**：在下一轮开始前才检查，输入本身也消耗 token，一次请求可能越过阈值；拿不到 usage 时无法精确累计。`max_tokens` 限制本次输出，也不能保证整次任务费用。流持续有数据时，读取超时不等于整个任务的硬截止时间。严格预算还需要输入估算、预留额度、总截止时间、取消和计费记录。

工具执行后，如果没有下一轮额度，必须明确任务未完成。不要把工具结果的一部分直接伪装成模型完成的结论。

## 以后怎样加重试

确认是临时故障后，可用有限次数的指数退避和随机抖动；例如最多重试两次，并尊重服务端的限流提示。每一次实际尝试都应产生新的模型 span，包含 attempt 序号，避免把三次调用的费用藏成一次。

鉴权失败、无效参数、未知工具通常要改输入或配置，重复发相同请求没有帮助。客户端超时并不说明服务端没有处理，因此重试模型请求可能重复消耗 token。

更关键的是有副作用的工具：写订单、扣款、发邮件不能盲目重试。设计幂等键、执行记录与确认机制，再决定能否重复执行。当前乘法工具无外部副作用，方便先学习协议。

## 权限来自应用，不来自模型

工具 schema 只描述格式，不能赋予权限。模型输出的名称与参数都应被视作需要检查的输入。白名单、参数检查、路径范围和数据库权限必须在应用侧执行。

后续增加读文件工具时，应限定根目录、拒绝越界路径与符号链接逃逸、限制文件大小。增加写入或外发工具时，要明确用户授权和可审阅的具体内容。检索到的网页、邮件和文件属于资料，其中的“请执行命令”不自动成为应用指令。

提示注入不是仅靠在 system prompt 写一句“不要被攻击”就能解决。缩小可用工具范围、降低权限、验证结果，通常比给模型更多自由更容易验证。

## 用离线测试学习失败

底层 `chat()` 不自动重试。使用回归测试检查模型请求失败、工具参数异常和预算耗尽时的实际行为。

```bash
uv run python -m unittest discover -s tests -v
```

这些测试用假 HTTP 响应代替 DeepSeek，用内存 exporter 代替 OpenObserve。它们不会花 token，也不会把测试噪音写进平台。重点读三个测试：

- `test_tool_loop_links_messages_and_spans`：确认工具结果确实进入第二次请求，并属于同一条 trace。
- `test_interrupted_stream_is_error_with_partial_response`：确认半句回答不会被当成完整成功。
- `test_partial_rejection_is_not_success`：确认上报接口 HTTP 200 但拒收部分 span 时，不误报成功。

练习：修改假工具参数，让它出现字符串、bool、额外字段、无穷值。再让假模型一直请求工具，验证循环会停止。不要为了制造这些错误去反复调用真实服务。

学会的标志：给你一条失败 trace，你能说出失败发生在哪层，为什么该重试或不该重试，以及是否已经发生外部副作用。
